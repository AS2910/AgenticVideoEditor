# What you need to set up

## For the public launch (2026-11-04), in order

1. **A server and a domain**: one VM (2 vCPU, 4 GB RAM, 80 GB disk is enough to start) with Docker Compose, a domain and its DNS A record pointing at the VM. Follow `DEPLOY.md` (Caddy gets the HTTPS certificate on its own). Nothing was created tonight.
2. **Production variables** in `.env` on the server (mode 600), checked by `make launch-check` (or `cd backend && python -m app.tools.env_check --env-file ../.env`): `AVE_ENV=production`, `AVE_AUTH=accounts` (or `google` with `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`), `AVE_SESSION_SECRET` and `AVE_SHARE_SECRET` (each `openssl rand -hex 32`), `AVE_PUBLIC_URL=https://<your domain>`, `ANTHROPIC_API_KEY`, `ELEVENLABS_API_KEY`, `OPENAI_API_KEY`, `AVE_EMAIL_PROVIDER=resend` with `AVE_EMAIL_API_KEY` and `AVE_EMAIL_FROM`, `AVE_LAUNCH_PROFILE=public`, `AVE_ADMIN_OWNERS=<your owner id>` (sign up first, then read your id from the Admin page or the database), `AVE_DAILY_SPEND_CAP_USD` (default 50).
3. **Email**: a Resend account, a verified sending domain (SPF and DKIM records at your DNS host). Sign-up, verification and password reset emails depend on it.
4. **Database**: SQLite on the server's disk is fine for launch. For Postgres, a managed database and `DATABASE_URL` (section "Postgres" below).
5. **Backups off the machine**: object storage (for example an S3 bucket or Backblaze B2) and `rclone` on the server to copy `/data/backups` there nightly (OPS.md).
6. **Error tracking**: a Sentry project and `SENTRY_DSN` (optional; errors are also in the log and on the Admin page).
7. **Payments**: Stripe and/or Razorpay keys and webhooks (section G3 below). Until then billing stays in test mode and the free trial's credits are the only ones anyone gets.
8. **Legal**: the Terms, Privacy and Acceptable use pages are drafts; a lawyer must replace them, then bump `AVE_TERMS_VERSION`.


- B3/F6 share links: set `AVE_PUBLIC_URL` to the address people open the app at (default `http://localhost:5173`), or links will point at localhost. Optional: `AVE_SHARE_SECRET` (a long random string) to sign links; without it one is generated into the data dir (`share_secret`) on first start; keep that file if you move the data dir, or every link stops working.
- B3 captions in non-Latin scripts (Hindi, Tamil for B2): the installed ffmpeg has no libass. Install an ffmpeg built with libass (for example `brew install homebrew-ffmpeg/ffmpeg/ffmpeg`) and the subtitles filter is used automatically; until then captions are drawn with OpenCV (Latin letters only).
- C2 email (review digests, new-version emails, review invites; item 7): every email is written to the `notify_outbox` table until Resend is set up. To send for real: a Resend account, a verified sending domain (SPF, DKIM, and a DMARC record), an API key with sending access, then `AVE_EMAIL_PROVIDER=resend`, `AVE_EMAIL_API_KEY=<key>` (or `RESEND_API_KEY`) and `AVE_EMAIL_FROM` (for example `Voltage <hello@yourdomain>`, on the verified domain). Without the key or the from address it stays on the outbox and logs a warning. Sent emails still get an outbox row (provider `resend`, or `resend (failed)` after the retries). Postmark or SES would be another `EmailSender` in `backend/app/notify/email.py`. Set `AVE_NOTIFY_OWNER_EMAIL` to where your own digest should go while sign-in is off; signed-in owners get theirs at their Google email. `AVE_PUBLIC_URL` must be the public address, or review links in emails point at localhost.
- G1 import from YouTube (a video you own): off behind the `LinkImporter` interface (`backend/app/linkimport.py` `YouTubeOwned`). To turn it on: a Google Cloud OAuth client with the YouTube Data API v3 enabled and the `youtube.readonly` scope (verification by Google is needed for that scope), a consent screen, then an implementation that lists the signed-in user's own uploads to prove ownership and a downloader for the owner's file. Google Drive and Dropbox public links need nothing set up.
- G2 invites and email sign-in: both send through the notify interface, so until a real email provider is set up (see C2 above: Resend, a verified sending domain, `AVE_EMAIL_PROVIDER=resend`, its key and `AVE_EMAIL_FROM`) invite and sign-in emails land in the `notify_outbox` table only; the Members page's Copy link still works for invites. Email sign-in shows only with sign-in on (`AVE_AUTH=google`) and `golive.g2` on for the default owners; `AVE_ALLOWED_EMAILS` still limits who gets a link. Invites need sign-in on to be accepted.
- G8 error reporting (item 7): reports always go to the server log and the local `error_reports` table (shown on the admin page). To also send them to Sentry: create a Sentry project and set `SENTRY_DSN` (the project's DSN, `https://<key>@<host>/<project_id>`); events are posted to its envelope endpoint over HTTPS with no SDK, scrubbed of cookies, authorization, request bodies and secret-looking values. Allow outbound HTTPS to the DSN's host. For the browser, keep posting to `POST /errors` (it forwards through the same reporter) or add the browser SDK with the same DSN.
- G3 billing (item 7: real providers are built, off until their keys are set; without keys everything stays fake, test mode). Webhook URLs below are the backend's public address (where `/billing/...` is served; behind the frontend proxy that is `<AVE_PUBLIC_URL>/api`). **Stripe** (international, USD): a Stripe account (activated for live payments), a secret key `AVE_STRIPE_SECRET_KEY` (`sk_test_...` for test mode, `sk_live_...` for live; a restricted key needs Checkout Sessions and Refunds write), and a webhook endpoint in the Dashboard (Developers, Webhooks) at `<backend>/billing/webhooks/stripe` for `checkout.session.completed` and `checkout.session.async_payment_succeeded`; its signing secret is `AVE_STRIPE_WEBHOOK_SECRET` (`whsec_...`). Stripe is used only when both are set. No Products or Prices are needed (Checkout uses the prices in `backend/app/billing/__init__.py`). Set `AVE_PUBLIC_URL` so the success and cancel pages return to Billing. **Razorpay** (India, INR): a Razorpay account with KYC done, API keys `AVE_RAZORPAY_KEY_ID` and `AVE_RAZORPAY_KEY_SECRET` (`rzp_test_...` or `rzp_live_...`), Payment Capture set to automatic, and a webhook (Settings, Webhooks) at `<backend>/billing/webhooks/razorpay` for `payment.captured` with a secret you choose, `AVE_RAZORPAY_WEBHOOK_SECRET`. Razorpay is used when the key id and secret are set; without the webhook secret the webhook route is off and the signed payment from checkout.js (`POST /billing/razorpay/verify`) grants alone. **Frontend, still to do**: with keys, buying answers `checkout.url` (redirect to Stripe) or `checkout.client` (open Razorpay checkout.js with it, then post the result to `/billing/razorpay/verify`); the Billing page does not do that yet. Refunds: an admin calls `POST /admin/billing/refund {owner, invoice_id}` (full refund, credits taken back); refunds made in the providers' dashboards are not picked up. **GST**: register for GST and set the seller's legal name, GSTIN and state (`AVE_SELLER_NAME`, `AVE_SELLER_GSTIN`, `AVE_SELLER_STATE`, default 29 Karnataka as a placeholder); file a Letter of Undertaking (LUT) so exports of services are zero-rated as invoiced; have an accountant confirm the SAC code (998314), invoice numbering (`VLT-YYYYMM-NNNNN`, one series) and the INR prices. Prices, credits per plan, the 5 trial credits and the top-up markup (1.2) are placeholders in `backend/app/billing/__init__.py`.
- G6 trust and safety (all fake now): **Liveness**: pick a provider (speech-to-text match of the read sentence plus a voice match against the video's speaker and replay detection, e.g. a speaker-verification API) and implement `LivenessProvider.verify` in `backend/app/safety/liveness.py`; until then `FakeLiveness` passes any readable recording of a second or more (test mode). **Public figures**: `backend/app/safety/public_figures.txt` is a small hand list matched by name; a real check compares the voice itself against a reference set (a vendor's celebrity voice blocklist or a speaker-ID service) behind `PublicFigureCheck`. **Watermark**: `FakeWatermarker` writes the mark into the MP4 metadata (removable); a real one embeds it in the audio and the picture and survives re-encoding (for example AudioSeal for audio, or a commercial service such as Digimarc or Steg.AI) behind `Watermarker`. **C2PA**: `FakeSigner` signs with an HMAC (test key derived from the share key); real signing needs an X.509 signing certificate from a CA on the C2PA trust list and `c2patool` (or the c2pa SDK) to embed a signed manifest in the MP4 and keep the `.c2pa.json` sidecar. **Legal**: the Terms, Privacy, Acceptable use and Sub-processors pages are v2 drafts marked "Draft, needs legal review" (text in `frontend/src/pages/legal/`), each open point a "For counsel" note; a lawyer must review them, fill the placeholders (company, address, Grievance Officer, regions), confirm the 7-year consent-record retention (`AVE_CONSENT_RETENTION_YEARS`), the data-export contents and the account-deletion wording. **Abuse reports**: set `AVE_TRUST_EMAIL` to the trust and safety inbox (reports also reach the admins' bell) and a real email provider (see C2).

## Postgres

- **Default is SQLite** (`backend/var/ave.db`). To run on Postgres, create a managed Postgres 14+ database (Neon, Supabase, Amazon RDS, Cloud SQL or similar) and set `DATABASE_URL=postgresql://USER:PASSWORD@HOST:5432/DBNAME` (add `?sslmode=require` for most managed hosts) in `backend/.env` or the server's environment. The driver is `psycopg[binary]`: `pip install -e 'backend[postgres]'` on the server.
- **Migrations** run at startup as on SQLite. To run them by hand: `cd backend && python -m app.store.migrate status --db "$DATABASE_URL"`, then `up` (all pending) or `down N`. The same `--db` URL works for `python -m app.purge` and `python -m app.flags`.
- **Moving data from SQLite**: not automated. A one-off copy is `python -m app.store.migrate up --db "$DATABASE_URL"` on an empty database, then copying each table's rows (for example with `pgloader`), then resetting the id sequences (`SELECT setval(pg_get_serial_sequence('t', 'id'), MAX(id)) FROM t` per table with an `id`, and the same for `rowid`).
- **Row-level security (migration 0034)**: every table with a `workspace_id` has RLS enabled and a `ws_scope` policy, but it is **not enforced yet**: the app's connection sets `app.bypass_rls = on`, and a table's owner skips RLS anyway. To enforce: (1) run the app as a role that does not own the tables and is not a superuser (grant it SELECT, INSERT, UPDATE, DELETE on the tables and USAGE on the sequences); (2) per request, in the transaction, `SELECT set_config('app.workspace_id', '<the workspace id>', true)`; (3) stop setting `app.bypass_rls` for request connections (`backend/app/store/pg.py` `connect`), keeping it for migrations and admin jobs.
- **Testing on Postgres**: `pip install -e 'backend[postgres-test]'`; `pgserver` gives a throwaway local server (`python -c "import pgserver; print(pgserver.get_server('/tmp/avepg', cleanup_mode=None).get_uri())"`); set `AVE_TEST_DATABASE_URL` to that URL and run the backend suite. Each session gets its own database, dropped at the end; tests that open the SQLite file directly are marked `sqlite_only` and skipped there.
